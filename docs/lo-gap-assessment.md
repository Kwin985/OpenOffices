# 与 LibreOffice 26.8 的差距评估

评估日期：2026-10-21 · 对标版本：**LibreOffice 26.8.1**（2026-10-08，最新稳定分支）
本方版本：工作树 v0.96.0 + v0.128–v0.137 十轮未提交迭代（下称「本项目」）

> 这份评估的读者是「下一步做什么」的决策者，不是宣传材料。所有数字都要么来自本仓库
> 可复算的量具（`scripts/fidelity-report.mjs`、路线图勾选统计、`wc -l`），要么来自 LibreOffice
> 官方发布页与发布说明；**没有**凭印象给的数。给不出数的地方写明「未量」，不猜。

---

## 一、结论先行

三句话，按「能用 / 深度 / 广度」三层分开说，混在一起会得出错误结论：

1. **主链路能用**：三件套（文档/表格/演示）的「打开 → 编辑 → 保存 → 导出 PDF」全通，
   PDF 查看/标注/页面管理也全通。在中文用户的日常场景里，它是可用的替代品。
2. **深度差一个量级**：本项目**自己量出来**的 docx 属性级覆盖率是
   **17.6%（按不同属性对）/ 50.7%（按字面量）**（313 份真件 / 302 MiB / 682 个有意义属性对，
   查问了 120 个）。这是全篇最硬的一个差距数字——它量的是「真件放到线上那些属性，我们的
   导入路径到底问过几个」，不是「实现了多少个命令」。
3. **广度差得更多**：LibreOffice 六件套（Writer/Calc/Impress/Draw/Base/Math），
   本项目是三件套半（文档/表格/演示-lite + PDF 侧线）。Base、Math、Draw 三块**完全没有**，
   数据透视表、邮件合并、文档比较、无障碍、多语言词典这几块**零覆盖**。

一句话归纳：**深度差 1 个量级，广度差 1.5 个量级；但在「只做对的那一半」里，
本项目有几处纪律比 LibreOffice 严。**

## 二、口径先说清楚（这三条混着比会得出荒唐结论）

### 1. 物种不同：自绘原生套件 vs Web 内核组装

| | LibreOffice | 本项目 |
|---|---|---|
| 排版引擎 | 自有（VCL + 自有排版/断行/连字/基线网格） | WebView2（Chromium 的 CSS Paged Media） |
| 字体 | 自有（含 OpenType 变体、CTL/RTL 整形） | 系统字体 + 浏览器 |
| 文件格式层 | 自有过滤器（C++，几十种） | Rust（`calamine` / `rust_xlsxwriter` / `quick-xml`）+ TS 侧直读直写 |
| 天花板在谁手里 | 自己 | Univer / TipTap / pptxgenjs / pdf.js / pdf-lib / Chromium |

**这一条决定了差距的性质**：本项目在「打印保真」上遇到的每一个坑（`@page` 串台、`:first`
穿透、`color-scheme:dark` 把画布涂深、`:odd/:even` 不被认）本质上都是**Chromium 的 CSS
分页媒体支持度**问题，不是本项目能靠代码纪律彻底解决的。LibreOffice 直接画纸，没有这一层。

反过来，这一条也带来一个 LibreOffice 拿不到的东西：本项目的界面是 React 19 + CSS，
改一个主题不用重编译 C++，而 LibreOffice 直到 26.8 才做到「改主题颜色不用重启」。

### 2. 目标不同：「全」vs「准」

LibreOffice 的目标是「覆盖 MS Office 的全部功能面 + ODF 全谱系 + 六个组件」；
本项目的目标是「主流文件的**保真往返**」。README 里那句「天下苦 WPS / Office 久矣」和
「数据全程不出本机」说明定位是：**本地优先、格式保真、够用就好**，不是功能清单对齐。

所以「功能数量」这个口径对本项目不公平，但也不是借口——`docs/fidelity.md` 那 17.6%
是本项目**自己选的尺子**量出来的，它认这个口径。

### 3. 「未勾 425 项」不等于「425 个功能没有」

这是最容易误读的一个数。抽样看那 425 条，绝大多数是**验证欠账**而不是**功能缺口**：

```
425 条未勾里，命中这些词的条数：
  没量 21   未量 27   只量 6    量具 11   A/B 11
  dev 27    release 21   真机 19
  （合计去重前已超过 140 条，且这些词大量共现）
```

典型样本：

- 「v0.92 没有 release A/B」——功能是有的，缺一次 release 上的对比测量
- 「字符间距的屏上后果没量」——字节写对了，屏上没量
- 「嵌套表的版心是按最外层算的近似」——做了，是近似
- 「换一台机器、换一批件就不可复核」——量具纪律

真正的**整块功能缺口**在路线图里根本没出现（因为没立项），比如：
`Base` / `数据库` / `邮件合并` / `主控文档` / `比较文档` / `无障碍` / `屏幕阅读` /
`断字` / `同义词` / `国际化` / `多语言` / `RTL` / `OpenType` / `Basic` / `数据透视`
——这 15 个关键词在 1641 行路线图里**勾=0 且 未勾=0**。

**所以 425 这个数读作「已立项目的验证欠账」，不是「功能差距」。功能差距要看上表那 15 个零。**

### 「按使用频率加权的功能等价度」估计

不能精确算，但可以给一个有依据的区间，并说明依据：

- **日常主链路**（打开/编辑/保存/导出 PDF/打印/查找替换/批注）：**70 ~ 85%**
  ——依据：路线图 161 项已勾里，PDF 24、导出 14、打印 11、docx 18、odt 19 全部在册，
  三件套核心交互无缺口。
- **专业/长尾功能**（数据透视、矢量绘图、数据库、公式编辑、宏、多语言、无障碍）：**< 15%**
  ——依据：15 个关键词在路线图里勾=0 未勾=0，即未立项。
- **综合加权**（按普通用户的功能触及频率，主链路权重约 0.8）：**约 30 ~ 40%**

**这个 30~40% 不等于「还差 60~70% 的活」**：因为 LibreOffice 那 60~70% 里有一大半是
本项目按定位**不打算做**的（Base、邮件合并、100 语言……）。若只算「本项目打算做的那部分」，
完成度大概在 **50 ~ 65%**。

## 五、差距的性质（三条洞察）

### 洞察 1：差距主要是「广度」，不是「已做部分的精细度」

在已经做的那部分上，本项目的精细度**不低于** LibreOffice：表样式条件层的五层梯子、
`w:tblLook` 闸门、ODT 列表按层取档 + 编号形状 + 起号两家 + 符面字符与专字两条通道、
页眉页脚十六格 `@page` margin box 复位——这些是 LibreOffice **不需要**做的：
它的 ODF 是原生格式，docx 才是外来格式，它没有「反向工程 OOXML 语义」这层工作。

本项目的独特工作量恰恰来自定位：**把 docx / ODF / pptx / xlsx 全当外来格式做双向保真**。
这条路 LibreOffice 只在 docx/xlsx/pptx 那一侧走（且走了 20 年）。

### 洞察 2：17.6% 这个数要按「字面量 50.7%」一起读

`docs/fidelity.md` 自己给了两个口径：

- **17.6%** = 682 个不同的 `元素|属性` 对里查问了 120 个 → 这是**长尾**的账
- **50.7%** = 2,337,889 个有意义字面量里查问了 1,184,292 个 → 这是**高频**的账

高频属性大多覆盖了（`w:sz`、`w:color`、`w:jc` 之类），长尾没碰（`rFonts|hint` 136,408 枚、
`szCs|val` 96,610 枚）。**用户实际感受更接近 50.7%**，而「打开一份没见过的文件会不会掉格式」
更接近 17.6%。两个数都要看，只看一个会得出相反的结论。

### 洞察 3：425 项未勾的构成决定了「下一轮做什么」

按关键词采样，425 条里：

- **验证欠账**（没量/未量/只量/量具/A/B/dev/release/真机）：**约 140+ 条**，占三成以上
- **精度近似**（「是近似」「简化账」「按最外层算」）：一批
- **真功能缺口**（「未接」「不认」「没做」）：少数，且多数是 ODS/ODF 侧的三变体属性
  （`-asian` / `-complex` 字族字号、`office:font-face-decls` 映射）

这意味着：**继续提高「已做部分的可信度」的边际收益，正在低于「补长尾属性」的边际收益。**
前九轮（v0.128–v0.136）连续七轮都在做加固与补测试，这条曲线该拐弯了。

## 六、追赶建议（按 ROI 排序）

### 第一档：边际成本最低、量具现成（建议立刻做）

1. **长尾属性补覆盖**：17.6% → 30%。`scripts/fidelity-report.mjs` 已经把「never consulted」
   按字面量排好序了（`rFonts|hint`、`szCs|val`、`lsdException|name` …），
   **从上往下做就是了，不需要重新定义做什么**。这是全项目 ROI 最高的一件事。
2. **ODF 三变体属性**：`style:font-name` / `fo:font-size` 的 `-asian` / `-complex` 两枝
   （已在未勾里立案，是真缺口不是验证欠账）。

### 第二档：能力形态的缺口（值得立项）

3. **图表原生化**：现在是「读元数据 + 渲染 PNG 浮动图」，不是可编辑的图表对象。
   这是表格侧最大的一块形态缺口（LibreOffice 26.8 都在补 `chartex` 六型往返）。
4. **Math 公式可编辑**：现在是线性化纯文本，Word 的 OMML 进来就不可逆。
   这块可以做小——接一个 MathML 编辑器（如 MathLive）比自建 Math 便宜得多。
5. **Draw 的最小可用子集**：不是复刻 Draw，而是让演示的形状层能独立出一张画布
   （流程图形状 + 连接线即可）。

### 第三档：明确不要追（追了也不划算）

- **Base**：数据库不是办公套件的主战场，且 Firebird/HSQLDB 是两个额外引擎。
- **邮件合并 / 主控文档 / 文档比较**：低频、长尾、和本项目的「本地保真」定位无关。
- **完整 Basic / UNO / ScriptForge（35 个服务）**：LibreOffice 的护城河，也是它的历史包袱。
  本项目的 VBA 子集已经覆盖了「跑通别人的宏」这个 80% 场景，够了。
- **100+ 语言 UI 与词典**：等真有非中文用户再说。

## 七、没量 / 不确定的（诚实清单）

- **表格函数覆盖度**：Univer 引擎提供了多少函数、缺哪些，**本项目从未量过**。
  上面表里写「未量」而不给数字，就是这个原因。要量就得先定「对谁量」（Excel 函数表？
  真件里用到的？）。
- **pptx / xlsx 的属性级覆盖率**：`fidelity-report.mjs` 目前只覆盖 docx（7 个部件）。
  表格与演示那两条腿**没有对应的公开账**——17.6% 不能外推到它们。
- **LibreOffice 的当前人力与代码量**：80 提交者 / 1600 提交 是 TDF 2015 年的口径，
  700 万行是 TDF Wiki 的口径，1000 万行是 2025 年官方博客的口径。三者不是同一年，
  本报告并列列出而不取平均。
- **真机对比**：本机没有装 LibreOffice（README 里那条「我们写的这一层别的应用认不认未证：
  v0.61 的四腿里没有第三方 Office 腿，本机无 LibreOffice/OpenOffice」就是这么来的）。
  **本评估的两方数据都是纸面对比，没有跑过一次真机对撞。**
