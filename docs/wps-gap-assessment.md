# 与 WPS Office 的差距评估（v0.173）

评估日期：2026-11-05 · 本方版本：仓库 `main` @ `c2b9a0f`（v0.172 之后的本轮）
对标对象：**WPS Office 桌面版（Windows）的常见功能面**——按桌面端本地编辑能力列举，
不做逐版本核对；云文档、AI、稻壳模板、会员增值、移动端不在口径内。

> 读者是「下一步做什么」的决策者。所有数字要么来自本仓库可复算的量具
> （`scripts/fidelity-report.mjs`、`scripts/fidelity-roundtrip.mjs`、
> `scripts/bench-docx-parse.mjs`），要么来自本次对 `src/` 的逐文件盘点。
> 给不出数的地方写「未量」，不猜。仓库里另有
> `docs/lo-gap-assessment.md`（2026-10-21 对 LibreOffice 26.8 的评估）与
> `docs/gap-closure.md`（2026-10-17 的补齐方案）——**那两份的结论已过期**：
> 当时 docx 属性级覆盖是 17.6% / 50.7%，P2 里的拼写、协同、VBA、PDF 改字
> 后来都已落地。本文件是当前状态的重新评估。

## 一、结论先行

按「能用 / 深度 / 广度」三层分开说，混在一起会得出错误结论：

1. **主链路能用**：Writer / Calc / Impress / PDF 四组件的「打开 → 编辑 → 保存 →
   导出 PDF」全通；docx / odt / xlsx / ods / pptx / .odoc / .opd 的读写链路齐，
   PDF 查看、标注、页面管理、原地加字也齐。中文用户日常场景是可用的本地替代品。
2. **深度差在「写回去」而不是「读进来」**：docx 保真账（读手按名查问过哪些属性对）
   已到 **99.0% 按对 / 98.4% 按字面**（合成语料 701 对，已到顶）；但往返账
   （源包 → HTML → TipTap → 写手 → 再普查）只有 **正文 246/300 = 82.0%、
   图形壳 28/319 = 8.8%、合计 274/619 = 44.3%**。读得懂、写不回，是当下最硬的一块差距。
3. **广度差在「外壳」而不是「引擎」**：四组件各自的编辑器里功能不少，缺的是
   WPS 那层「一眼认得出」的操作体系——无 Ribbon/菜单栏、内容区无右键菜单、
   无独立打印预览、Writer/Impress/Calc 无视图缩放、Impress 无母版编辑、无格式刷
   与导航窗格（**本轮补上**）、无页面边框 / 水印 / 邮件合并 / 公式编辑器 / 数据透视表。
4. **定位差异别当差距算**：WPS 的云同步、AI 写作、模板商城、多端协同是产品形态差异；
   本项目主打「数据不出本机 + 外来格式双向保真」，这几块**明确不追**。

一句话：**日常主链路约等于，专业长尾约等于零，最贵的一笔欠账是图形壳的往返。**

## 二、口径先说清楚

| | WPS Office 桌面版 | 本项目 |
|---|---|---|
| 排版引擎 | 自有（对标 MS Office 的排版/分页/域） | WebView2 / Chromium CSS Paged Media |
| 内核 | 自研全栈 | Writer: TipTap；Calc: Univer；Impress: 自研 + pptxgenjs；PDF: pdf.js + pdf-lib；读手/写手自研 |
| 格式立场 | docx/xlsx/pptx 是主要工作格式 | 全当**外来格式**做双向保真，另存自有 .odoc/.opd |
| 天花板 | 自己 | 上游库 + 浏览器分页媒体支持度 |

**这一条决定差距性质**：打印保真上的 `@page` 串台、`:first` 穿透、暗色主题涂纸，
本质是 Chromium 的分页媒体边界，不是代码纪律能彻底解决的；WPS 直接画纸。
反过来，界面是 React 19 + CSS，改主题不用重编译——这是 WPS 没有的成本结构。

第二条口径：**「功能数量」不能跨物种直接比**。本项目的目标不是「复刻 WPS 的命令清单」，
而是「主流文件进得来、出得去、不改样」。所以下表按「用户会不会撞上」列，
不按「WPS 有多少个按钮」列。

## 五、差距的性质（三条洞察）

1. **外壳层差距比引擎层更影响「像不像 WPS」**。用户判断一个办公套件，
   先找的是菜单、右键、格式刷、导航窗格、缩放和预览——这几样本轮之前一个都没有，
   而底下 docx 样式链的精细度其实已经不低于同类开源实现。补外壳的边际观感收益很高。
2. **「读得进写不出」是设计缺口，不是 N 个 bug**。往返账上掉了 328 对，
   其中图形壳占 289 对；逐对修要修到天亮，真因是模型没有对应的槽（v0.158 编号定义
   八对同源那条教训）。要动就得整族设计，不能按榜单逐个打补丁。
3. **天花板在上游**。Univer/TipTap/pptxgenjs/pdf.js 决定「能表达什么」，
   Chromium 决定「纸面长什么样」。WPS 自有引擎能改的东西，本项目只能绕或记账；
   所以「与 WPS 对齐」的合理目标是**主链路 + 高频交互**，不是全套命令。

## 七、追赶建议（按 ROI 排序）

**第一档：量具现成、改动局部**

1. **图形壳往返 8.8% → 往上推**：这是最大的一块，但要先定「哪些壳属性值得进模型」的口径，
   再整族设计，别按 289 对逐个打补丁。
2. **外壳补齐**：Writer 视图缩放 + 独立打印预览 + 内容区右键菜单（复制/粘贴/段落/表格），
   Impress 视图缩放与母版编辑入口，PDF 的查找替换。都是用户天天撞、单轮能做完的。
3. **D32 顺延清单**：`fldChar` 三对、`outline|val`、`col|w`/`col|space` 不等宽分栏、
   `smartTag|*` / `legacy|*`；`theme1.xml` 进不进普查清单仍要定口径。

**第二档：能力形态缺口，值得立项**

4. 原生可编辑图表对象（现在是 PNG 浮动图）。
5. Math 公式可编辑（现在 OMML 线性化成纯文本，不可逆）。
6. 数据透视表至少「建得起来」，PDF OCR / PDF→Word。

**第三档：明确不追**

- WPS 云文档、AI 写作、稻壳模板、会员、移动端、100+ 语言 UI；
- LibreOffice 那套 Base / Draw / Math 全组件（与「本地保真四套件」定位无关）。

## 八、没量 / 不确定的（诚实清单）

- **没跑真机 WPS 对撞**：仓库的实机回归是 Word 16.0 / PowerPoint 16.0 COM，
  本机没有 WPS 的自动化回归链路；本评估是纸面对照 + 本仓库量具，不是双份真件互撞。
- **WPS 功能面按桌面版常见形态列举**，未逐版本核对，也不含云/AI/会员增值。
- **xlsx / ods / pptx 的属性级往返账**：只有 pptx 有一份 77 对夹具的保真账，
  表格侧没有公开的属性级账；99.0% 不能外推到它们。
- **Univer 函数覆盖度**从未量过。
- **本轮性能数字来自纯合成夹具**（N 段同构段落、STORE 压缩），
  量的是解析与序列化成本，不是真件的打开耗时；真件上还有图片、样式、关系表的开销。
- **保真账的语料是合成重建件**（`--synth`，按 count/100 缩放）：
  按对可与旧账比，按字面不可比。
