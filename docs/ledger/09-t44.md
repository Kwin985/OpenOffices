## t44 前置实测（只量不改产品）ODT/docx/.odoc 三族解析那一段的分段构成与「最长同步块」两把尺 — 「解析仍是一口气」和「这口气在用户那头卡不卡」是两件事：v0.87 把打开链路拆成 `planFeed` 分批喂之后，roadmap 里留下一句「所以小件的最长同步块仍在解析上而不是编辑器上」，而这一句从写下那天起没有一把尺量过；本轮把这句话量到见底——`c1` 件面底数（86 枚：真件 ODT 76 + 真件 docx 1 + 合成三型三档 9）、`c2` 逐件分段（zip / 取文 / 解析 / 走树残差 + 尺C 最长空档）、`c3` 离线采样器校牙与两遍自同（86 枚出口 md5 逐枚同）、`c4` 尺E 增长律（两臂只差一枚 `text:style-name`）、`c5` 尺F CPU 自时间热点榜（`node:inspector`）、`c6` 调用枚数斜率榜（十把 jsdom 入口套计数器）、`c7` 尺G/H 宿主形状律（11 把尺 × 两档 N）、`c8` 原始计时与落地和、`s1` 屏上十枚件逐件总 + 最长同步块 + longtask 榜、`s2` 屏上形状指数对照离线同形状、`s3` 屏上采样器校牙、`s4` 五枚臂把 longtask 的记账口径定死、`g1` 吃十份日志原样合判（`押格枚=30 合枚=28 不合枚=2 只点名不判合的读数格枚=1 分箱合计=31 余数=0`），产品源文一寸没碰（`src/lib/odt.ts`、`src/lib/bullet-char.ts`、`src/components/DocEditor.tsx`、全部 Rust 与四枚版本文件一字未改），本轮造的件只是量具夹具。

- 裁定（`tmp/t44/price.txt` §一，写于任何装配动作之前）：**本轮以读数收尾，不实现「拆解析」**。三条现量依据：R1（`g1|6.2`）真件三枚屏上总=`[V_back.odt:31.3 tdf167774.odt:10.5 tdf116195.odt:12.2]` 而 longtask 榜=`[0 0 0]` ⇒「小件的最长同步块仍在解析上」这一句的**前提**不成立，真件解析压根没起过 ≥50ms 那一档；R2（`g1|6.1`+`g1|5.1`）只有 ≥8000 段那一档起单段长任务：`t44-8000.odt:80`、`t44-24000.odt:175`、`t44-24000.docx:73`，件枚=10 里出榜 3，而 `.odoc` 两档全不出榜；R3（`g1|1.1`+`c5`+`g1|4.3`）离线那枚平方在宿主：件面自时间 `attributes.js` 68.6% + `HTMLCollection-impl.js` 18.7% = 88% 而 `src/lib/odt.ts` 只 1%，24000 段离线 137,663.5ms 对屏上 196.9ms = 699 倍，屏上指数 ≤0.6 而正控制 1.87~2.15。代价面：把解析挪进 worker 或 Rust 要动的是整条读侧（`odt.ts` 2,304 行 + `docx-fidelity.ts` + jszip/xml-js 依赖 + 两处调用点）；收益面：R1 量到的是 0 枚真件长任务 ⇒ 按家规「不为假想需求设计」不立项，改为把 roadmap 那句前提改口成读数。**本裁定不许写成「已解决」**：解析仍是一口气（fid / odt / `JSON.parse` 三族同）这一句仍然真，收窄而不勾选（roadmap.md:703 仍是 `- [ ]`）。
- 件面底数（`c1`，86 枚逐件打「件字节 / 主件字符 / 侧件字符 / 顶层块 / 出口字符」）：语料=真件 ODT 76 + 真件 docx 1（`C004.docx` 字节=76,834 主件字符=256,699 顶层块=43 出口字符=126,493）+ 合成三型（odt / docx / odoc）三档（2000 / 8000 / 24000）九枚；最大那枚真件 `tdf107392.odt` 字节=43,344 而**出口字符=217,430**、`V_back.odt` 字节=64,222 主件字符=285,264 顶层块只有 44 而出口字符=120,032 ⇒ 件字节与出口字符不同量纲，任何「件大所以慢」的推理都得先换成顶层块数那一把尺（`t44-24000.odt` 字节=135,917 顶层块=24000 出口字符=1,201,780）。边界写明：本腿在 node+jsdom，DOMParser 的绝对毫秒不外推到 WebView2。

- longtask 的记账口径（`s4`，五枚臂定死「哪些任务进得了榜」；`臂枚=5 出榜臂枚=3 押格枚=6 合枚=5`）：`X1` 复现 `s3` 校牙①（烧 200ms 在 `Runtime.evaluate` 体内 + 等三枚 tick）榜枚=0 合=true；`X2` 先一枚 tick 再烧 ⇒ 榜=[200] 合=true；`X3` 烧在显式 `setTimeout` 回调体内 ⇒ 榜=[200] 合=true；`X4` 烧在 evaluate 体内而**后等 600ms** ⇒ 榜枚=0 合=**false**（押的是 A 档「等足真实时间就进账」，读数把它证伪了）；`X5` 正控制（真件 8000 段读手在 evaluate 体内）⇒ 榜=[58] 合=true 而墙钟=88ms 并排点名。`归因 B档(任务口径)证据=true A档(送达延迟)证据=false C档(活儿口径)证据=false 三档互斥否=true` ⇒ **榜记的是「浏览器派发的那一枚任务」而不是「活儿烧了多久」**，产品读手进账是因为它的活儿在 await 之后续起（`g1|5.5` 押 榜最大 ∈[50,200] 且 墙钟 ∈[50,200] 合=true ⇒ s1 的榜读数是产品态而不是腿造的）。`g1|5.3` 押 s4 X1 与 s3 校牙① 同致 合=true ⇒ `s3` 那一格 `合=false` 归因在**用法错**（把烧写在 evaluate 体内）而不是观察器瞎。第二把尺（`performance.getEntriesByType("longtask")` 缓冲差）五枚臂全程 0 ⇒ 无牙，`g1|5.6` 押「同致=false 的枚=3 而枚枚有榜 ⇒ false 归因于缓冲尺瞎而不是送达延迟」合=true。
